Why

A cut (a loop's head, a statement entry with several predecessors) resets heap knowledge to what it states. It restated an allocation's freshness by kind of binding: a let's cell apart from every older slot and some younger ones; a for...of iterator apart from older slots but fresh constants; an array literal's spine apart from older value slots' spines; an object literal a constant holds not at all. Each kind had its own partners, and safe programs outside the list were refused: two object literals where a write of the older one's field dropped the younger one's facts past a loop's head, and blocker-for-of-fresh-record, a let given a fresh record on each pass of a for...of loop, refused at the loop's entry because the iterator's separation from the let's fields held only while the let kept its first value.

Gap

new K() of a program's class and a factory make(): a code definition's call or construction states no fresh result (a stated Fresh<T> is a fresh spine, not a fresh object), so neither is fresh and both stay refused; making one fresh needs a contract stating it and a check certifying it.

Soundness

The restated separation is required knowledge of the entry: every incoming edge must establish it by the separation check proved for edges, so a pair stated wrongly is refused at its edge. A pair of a slot's value of the allocation's time holds by the allocation's freshness; a pair of named fields with a slot rebound to a later allocation is established by that allocation's own separation, in the other orientation.

Keep a fresh cursor's facts across a write of a parameter's field in a loop

no-behaviour-change
fresh-object-separation-loop.ts#walkfresh-object-separation-loop.ts#walkDefaulted

Why

In pretext's walkPreparedLinesRaw a fresh cursor { segmentIndex: 0, … } carries safeInteger(cursor.segmentIndex) && 0 <= cursor.segmentIndex through the loop's invariant, and the body writes stats.lineCount++ before a callee requiring those facts. The write x.f := v keeps a fact over z.g only where a separation fact states the two locations apart, or where z is x's object and g another key (write-sibling): that rule is right, since in the model two objects may share a location unless a fact separates them. The cursor's allocation separates it from stats.lineCount, but the loop's head stated no separation of an object literal a constant holds, so past it the write dropped the cursor's facts. The statement-entry separation of the previous commit states it; these cases show the shape at minimal size.

type Cursor = { segmentIndex: number; graphemeIndex: number };
type Stats = { lineCount: number; maxLineWidth: number };

/** @requires safeInteger(cursor.segmentIndex) && 0 <= cursor.segmentIndex */
function step(cursor: Cursor): number {
  return cursor.segmentIndex;
}

export function walk(stats: Stats, xs: readonly number[]): number {
  const cursor: Cursor = { segmentIndex: 0, graphemeIndex: 0 };
  const count = xs.length;
  /** @invariant safeInteger(cursor.segmentIndex) && 0 <= cursor.segmentIndex */
  while (cursor.segmentIndex < count) {
    const start = cursor.segmentIndex + 1;
    cursor.segmentIndex = start;
    stats.lineCount++;
    stats.maxLineWidth = step(cursor);
  }
  return stats.lineCount;
}
