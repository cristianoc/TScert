TScert · a cost regression

One condition, 300 MB of evidence

TScert regularly checks every function of its own front end, the code in tools/; that run is the census. On 2026-10-27 five branches were merged after commit 5dfb065, and the census after them verifies 15 more functions, but its proof search takes 3.4 times the CPU, and one run of the checker peaks at 10.6 GB. The cause is how TScert stores what it knows about object fields: a new fact about a field is added beside the old ones, never merged with them, so a condition testing one field n times stores a number of values growing as about n³. That storage is in the repository’s first commit; a rule merged that day made TScert’s own code reach it. This deck shows where, how it multiplies, which mistakes let it through, what the pass of work that followed changed, the second regression that pass found in itself, and what prevents a regression of this kind.

Words used in this deck

How TScert proves a function, in four cards

Search, evidence, checker

TScert verifies a TypeScript function by proving it safe. An untrusted search builds the proof, a JSON document called the evidence; a checker written and proved in Lean, a proof assistant, reads it and accepts or refuses. Both handle the same evidence, so its size drives the time and memory of both.

Slot

The checked program is a graph of steps, each storing its result in a numbered slot. Every read makes a new slot: reading node twice gives two slots holding the same object.

Heap fact

What is known at one point of the function about a field of an object: “the object in slot 4 has a field kind holding one of these values”. A fact is a slot, a field and a list of values. A test such as node.kind === 0 adds one on its edges.

Knowledge

The heap facts that hold at one point of the function. The evidence stores each distinct knowledge once, in a table, and each point refers to its entry by number.

Each ts.isX(n) is a call of TypeScript’s compiler API that tests n.kind, a field holding one of about 300 numbers, the members of the enum ts.SyntaxKind. Each guard that answers false adds a fact: n.kind is one of the numbers the earlier guards did not take.

Heap facts at successive points of the condition, with the rule, read from the evidence:

2, 6, 12, 20, 30, 42, 56, 72, 90, 110, 132

After k guards there are k × (k + 1) facts: both the facts on each slot holding n and the number of those slots grow with k (“What the points hold”, next). So the count grows with the square of the guards; each fact lists about 300 numbers.

Each failed test adds a fact to every copy of the object

type Kind = 0 | 1 | … | 99;

  • Old facts stay: each failed test adds a smaller list beside the earlier ones. The list of 97 values implies those of 98 and 99, which stay stored.
  • Every copy of the object gets one: several slots hold the object node refers to (the evidence links them as aliases: 4 after the 1st test, 6 after the 3rd), and each fact is stored once per slot. The last test answers by returning, so its fact reaches no stored point.
  • Answers are written out: “not 0” is the 99 other members of Kind, so a fact is as long as the type.
  • What is needed: one fact per point: after the 3rd test, node.kind is in Kind except 0, 1, 2. Stored instead: 18 lists, 1,764 values.

Four factors multiply; the first three grow with the number of tests n:

  • Facts per slot: one per failed test, about n.
  • Slots holding the object: they grow with the tests: 6, 10 and 18 at 4, 8 and 16 tests (n + 2).
  • Distinct points: each test’s edges carry their own knowledge, about n.
  • Values per fact: the size of the field’s type: 100 for Kind, about 300 for SyntaxKind.

So the stored values grow as about n³ times the type’s size, and the evidence 5 to 7 times per doubling. The growth is there without the rule.

What the branch changed

gap-nullable-field, commit a7b7843d, merged in 05041cf0 · added

A rule that keeps the facts across a call

The rule call-keep: a call whose declared effect (the fields its declaration says it may write) writes no field of an object that existed before the call keeps every heap fact (soundness proved in Lean, PromiseCalls.keepsHeap_prefix). Before it, every call ended with no heap facts. The branch also adds link-fact (a field read into a slot holds one of the values the slot’s type allows), which gives the extra fact per slot in 18 → 24.

Before the rule

each ts.isX(n) in visit is a call, so it ended with no heap facts, and no guard’s answer survived to the next guard: 0 facts.

With the rule

the compiler’s guards change nothing, so their calls keep the facts. The eleven guards now behave like a condition of eleven === tests: 132 facts.

The rule was reviewed as sound, and is. It did not create the growth: it removed the calls that had been hiding it.

The mistakes

Three mistakes let it through

1 · Storage with no normal form defect

Facts := List Fact (HeapFacts.lean:199): knowledge holds when every fact in the list holds. Nothing keeps one fact per field: a new fact is never merged with the facts on its field, a fact names a slot rather than the object, and an answer is the full list of values it leaves. All three are in the repository’s first commit, 2026-10-16.

2 · No test of how it scales defect

TScert’s test cases are small: each tests a few conditions, so a cost that grows with the length of a condition passes them all. No test measures how the evidence grows when a construct is repeated.

3 · Cost was not part of the merge defect

The branch measured only the functions it targeted (setLiterals: 433 KB of evidence in the census after the merge). The review asked about soundness, generality and tests. The integrating session, Claude, merged on passing tests. Only the census after the merge measured cost.

What the pass changed

commits 27798079 and 45bd0e40 · the theorems named are proved in Lean

Each fact stored once, about its alias class

Alias class

The slots known to hold one value: linked as aliases, or reading one field of one object. A class is named by its least slot. Facts are stored once, on that slot, and every rule reads a slot through its class.

Value set

A fact’s values are one set per kind of value; numbers and strings are written as these literals or as every literal but these. After three failed tests, node.kind is every number but 0, 1, 2: one fact, three literals.

Normal form

At each point but a cut (a point whose knowledge the source states), the search stores one fact per class and field, combining everything it knows there. Proved: it holds exactly where the stored knowledge does, and it is its own normal form (KnowledgeNormal.norm_holds, holds_of_norm, norm_idem).

Separation, and the evidence

Separation facts say two fields are different heap locations, so writing one keeps what is known of the other: a slot, some of its fields, and the slots and fields they differ from. They are stored grouped, proved to state exactly what they did and to be no more facts than before (compact_holds, compact_size). The evidence writes each distinct value set once, in a table.

A second regression, found in the pass

  • How it was found: the six costly functions of “Where it stands” were measured one by one against main, after their total had fallen; the total hid it.
  • What was observed: separation stored as single pairs, one per field on each side, sorted at every point, and restated on every slot of both classes whenever a step or an edge read it. Removing that removed the rise.
  • Fix: separation stored grouped (SeparationNormal.compact, proved to state exactly what the separation states). The checks that read it, at an edge and at a write, compare by class instead of restating (checkBy, apartBy, proved sound).

What prevents the kind

A bounded form, then measurement per function

In placeWhat it bounds
The normal form, proved to keep exactly what holdswhere it is stored, by its definition: one value fact per class and one field fact per class and field, whatever the number of tests
Value sets: what a test excludes is removed from one seta field’s tests at a point make one fact, not one per test
Grouped separation (compact_size, proved)no more separation facts than it is built from, each slot it differs from once, each field once

open: the scaling functions above (4 to 32 repetitions) as pipeline test cases, failing when the evidence grows faster than the repetitions; measuring each costly function against main before a change of the search or of Lean merges, as a written rule; a check that the evidence is in normal form; node.kind tested 32 times in one condition, which still exceeds the 60 s limit.
