TScert · method effects in practice

Using method effects: examples and outcomes

TScert checks type claims about TypeScript programs: it verifies a function when it proves the function safe, and otherwise refuses it (next slides). A function can state what it may change, and TScert checks the statement against the function’s body. Statements are certified (next slides) on test cases and on 61 functions of TScert’s own parser for TypeScript (“What expr’s statement rests on”). Of 16 parser functions measured, 11 verify (census of 2026-10-24): 9 verify in the census before the statements too, and 2 verify relative to statements that are audited, not certified, among them that of expr, the parser’s expression parser, at one call of Array map (“pattern’s map relies on the expression parser’s statement”; what it takes and what to expect follow there). The 16 are described on “More terms, for TScert’s own source”.

Words used in this deck

How TScert works, in three cards

Verified, refused

TScert verifies a function when it proves it safe: every value the function reads, writes or returns has its declared type. Otherwise it refuses the function, naming the first place it could not prove.

Statement

An effect is what a call may change; in this deck a statement is an effect a function declares in its result type (“What you write”), bounded by a footprint (“The footprint F”). A statement of TypeScript code, such as an if, is called a TypeScript statement.

Producer and checker

TScert’s parser, its front end, reads the TypeScript source; it is trusted, and reviewed by hand. From the parser’s output an untrusted producer proposes type claims (the types it asserts each value has) and effects, also of code that states none, and an untrusted search looks for their proofs. Untrusted: their mistakes cannot make TScert accept, since a checker, written and proved in Lean, a proof assistant, accepts only what it checks.

Words used in this deck, continued

Three more cards

Certified, relative

A statement is certified when the checker has checked the function’s own body against it, in a run that verifies (a run: TScert checking one source file, or a slice, “More terms, for TScert’s own source”; it verifies when every function in it does). A function that relies on a statement not certified is verified relative to it: proved assuming the statement holds.

Contract

TScert’s description of a built-in or library function, such as Array’s map or a method of TypeScript’s compiler API: reviewed by hand, and in parts proved in Lean (which parts: “Built-ins state footprints in their contracts”) against the steps the ECMAScript specification gives the function (lean/Verification/Semantics/FootprintNatives.lean).

Test case

A source file of TScert’s test suite with its expected outcome, verified or refused, such as method-effect-map.ts. A refused test case passes when TScert refuses it with the expected diagnostic.

The problem it solves

code adapted from test cases method-effect-map.ts and invalid-map-method-call-effect.ts · refused

If map’s callback calls a method known only by its type, the result may have holes

// Log: a class with a method

// note(n: number): number

function notes(log: Log,

    xs: number[]): number[] {

  const r: number[] =

    xs.map((x) => log.note(x));

  return r;

}

Holes. TScert reads number[] as: every index below the array’s length reads a number. A missing index, a hole, reads undefined, so an array with holes is no number[] to TScert (TypeScript’s own number[] admits one). xs is a number[], so it starts with no holes.

map and its callback. map reads the array’s length once, then visits each index, skipping one that is missing and leaving a hole there in its result. A callback that removes elements of xs during the walk (pop, shift, setting length smaller) makes later indices missing; log.note could, if log holds a reference to xs.

What TScert cannot see. For a call of a non-generic function declaration of the same module that no code reassigns, TScert finds the effect from that function’s code. log.note(x) is a method call, and its code depends on the value: log may be any value of type Log, an instance of a subclass that overrides note or another object of the same shape. So TScert assumes the worst: map’s result may have holes, and the function is refused at the assignment to r.

The answer. The effect is written once, on the method’s declaration, and checked there; every value the program introduces at the type is checked against it, an overriding method where its subclass is declared and any other object where it is passed as a Log; a value from outside code, such as an input of a checked function, is assumed to meet it.

What you write

from test case method-effect-map.ts · verified

The effect goes in the result type, as Within<F, T>

note(n: number): Within<{ value: "any"; store: "grow" }, number> {

  this.entries.push(n);

  return n + 1;

}

  • Within needs no import, only its declaration file listed in the project’s tsconfig.json: it is a global type alias in tools/resolvable.d.ts (tools/, the directory of TScert’s TypeScript front end). To TypeScript, Within<F, T> is just T, so the code compiles and runs unchanged. TScert recognises Within by that declaration, or an identical copy of its file: another type called Within is an ordinary type.
  • To TScert it is a statement about the call: on a normal return, the call changes memory that existed before it at most as F, the footprint, allows. With onThrow: true in F, this holds also when the call throws; without it, the statement says nothing about a throw.
  • F has the fields value and store, whose settings the next slide lists, and optionally onThrow: true; in prose this deck writes the settings without quotes. note states store: grow (it keeps arrays’ hole-free prefixes hole-free, next slide, as its push onto entries, a number[] field of its class Log, three slides on, does) and value: any, because push’s contract states value: any (two slides on).
  • TScert checks the function’s own body against the statement in a run that includes its definition, whether or not any code calls it; the statement is certified when that run verifies. Callers rely on the statement.

The footprint F

Two dials: ordinary locations and arrays

In TScert’s model an array is a store, the list of its element locations, and each element is a location holding a value. store bounds changes to stores: which indices hold an element. value bounds changes to every other location, the ordinary ones: object fields, variables, and the contents of array elements. Each dial orders its settings keep, then grow (store only), then any; one footprint is within another when each of its dials allows no more. Memory the call allocates itself is always free to change.

value: keep ⊑ any

store: keep ⊑ grow ⊑ any

store: keepno change to any store—
store: growevery hole-free prefix of an array (indices 0 to k−1, all holding elements) stays hole-free; unshift moves elements, which rewrites their contents and so also needs value: anypush, unshift
store: anyany change to storespop, shift, shortening length, reverse (on an array the call did not allocate; on one with holes, reverse moves them)

The footprint F, continued

Built-ins state footprints in their contracts

  • push’s contract is value: any, store: grow. store: grow is proved in Lean from push’s steps in the ECMAScript specification (theorem Arr.push_grow, lean/Verification/Semantics/FootprintNatives.lean). The part reviewed by hand says that push changes nothing but its array’s store and its elements’ contents. It allows changes to the contents of elements that existed before the call, which are ordinary locations, so it states value: any; by the ECMAScript steps, push itself writes only indices past the old length, and TScert states no tighter contract for it.
  • map’s contract has five signatures: four for a hole-free array and a callback within one of the footprints (value, store) {keep, keep}, {any, keep}, {keep, grow} or {any, grow}, each with a hole-free result, proved (map_rely, FootprintNatives.lean) assuming map tests presence only between callbacks (reviewed by hand), since map reads the length once and grow keeps the indices below it, and each giving the whole map call the callback’s footprint, so a caller keeps what that footprint preserves; and one for any array and callback, whose result may have holes (a callback with store: any may remove elements). Any of the four that the callback’s footprint is within gives a hole-free result; that footprint is found from the callback’s code and its callees’ statements and contracts.
  • value: any, store: any is refused as a statement: it states nothing.

Example that verifies

abridged from test case method-effect-map.ts · verified

A method that only appends keeps map’s result hole-free

export class Log {

  entries: number[] = [];

  note(n: number): Within<

    { value: "any"; store: "grow" }, number> {

    this.entries.push(n);

    return n + 1;

  }

}

export function notes(log: Log,

    xs: number[]): number[] {

  const r: number[] = xs.map((x) => log.note(x));

  return r;

}

Checked at the method: its body only pushes onto a field, which is within value: any, store: grow.

Used at the call: the callback calls a method stating store: grow, so TScert uses one of map’s hole-free signatures, and the assignment to r verifies. If log is an instance of a subclass the program declares, that subclass’s note is checked against the same statement.

Without a statement such a call is refused: test case invalid-map-method-call-effect.ts has a class whose method states no effect, called the same way.

Three statements that fail their check

A body that breaks its statement. bump states that nothing changes, but pops the array it is given (invalid-method-effect-method.ts).

class Bump { bump(xs: number[], x: number): Within<{ value: "keep"; store: "keep" }, number> {

  xs.pop(); return x; } }

An unstated call inside. run states that nothing changes and calls this.helper. Though helper changes nothing, a Runner may hold there any function of the field’s type, which states no effect (“Contract closure”, later; invalid-method-effect-unstated-dependency.ts).

function helper(xs: number[], x: number): number { return x; }

class Runner { helper: typeof helper = helper;

  run(xs: number[], x: number): Within<{ value: "keep"; store: "keep" }, number> {

    return this.helper(xs, x); } }

An override. Drain.take overrides Base.take and pops; the override need not repeat Within: its body is checked against Base.take’s statement (invalid-method-effect-override.ts).

class Base { take(xs: number[], x: number): Within<{ value: "keep"; store: "keep" }, number> { return x; } }

class Drain extends Base { take(xs: number[], x: number): number { xs.pop(); return x; } }

A generic function declaration may carry a statement: its annotated parameters are its inputs, so it is certified over its whole written signature. Its callers ignore the statement, so a map callback calling one gets map’s signature with holes: the generic declaration’s instances carry no footprint at that call.

Where you can write it

At the result of a signature: methods, interfaces, function types

An interface member · method-effect-interface.ts verified

interface Limit { over(n: number): Within<{ value: "keep"; store: "keep" }, boolean>; }

function firstOver(limit: Limit, xs: number[]): number { return xs.findIndex((x) => limit.over(x)); }

Each object passed where a Limit is expected is checked against the statement there. findIndex visits every index, reading a hole as undefined; with a callback that changes nothing, as here, the hole-free xs stays hole-free and each x is a number; without the statement x could be undefined, which over does not accept.

A function type, here a parameter’s · method-effect-callback-parameter.ts verified

function mapped(xs: number[], f: (x: number) => Within<{ value: "keep"; store: "keep" }, number>): number[] {

  const r: number[] = xs.map((x) => f(x)); return r; }

map’s result is hole-free; an arrow passed as f is checked against f’s statement where it is passed: one that pops xs is refused (invalid-method-effect-callback-argument.ts).

Where you can write it, continued

adapted from method-effect-field.ts, method-effect-onthrow.ts · verified

A field holding a module function, and a throw as an exit

A field holding a module function

function scaled(this: Scale, n: number): Within<{ value: "keep"; store: "keep" }, number> {

  return n * this.factor; }

class Scale { factor: number = 2; scaled: typeof scaled = scaled; }

A module function is a top-level function of a module; this: Scale is TypeScript’s this-parameter. The field’s type is the function’s own, statement included, so a call s.scaled(x), for s: Scale, relies on it; a function written into the field is checked against that type. (Runner’s helper field, on “Examples refused”, has the type of a function stating nothing.) TScert’s own parser holds many functions this way (later slides).

A throw as a possible exit

positive(n: number): Within<{ value: "keep"; store: "keep"; onThrow: true }, number> {

  if (n < 0) throw new Error("negative"); return n; }

// c: Check, the class of positive; xs: number[]

const r: number[] = xs.map((x) => { try { return c.positive(x); } catch { return 0; } });

The callback returns normally from its catch block, so what positive changes when it throws counts toward the callback’s return: with onThrow, nothing, and map’s result is hole-free. Without onThrow the throw is unbounded (refused variant: invalid-method-effect-stated-throw-caught.ts).

Two rules that decide how far it reaches

A statement holds everywhere and depends on its callees

Over the whole domain

The statement must hold for every receiver and argument the signature admits. An arrow’s or function expression’s statement is proved once, at a signature admitting every argument its annotation admits, so it does not depend on what a call site passes; a generic one is refused (“Forms that cannot carry a statement”).

Contract closure

A call through a method, field or parameter counts at the statement its type carries, since such a value may hold any function; one stating nothing defeats the statement. A stated function’s callees must be one of:

  • a method, field or parameter stating an effect within it;
  • a non-generic function declaration of the same module that no code reassigns (TScert finds its effect from its code), or an imported function stating an effect within it;
  • a built-in whose contract states a footprint within it;
  • for a statement without onThrow, a function whose result type is never (no normal return to bound);
  • a function defined in the body, whose own calls meet the same rule.

A try/catch in a stated body may catch a call’s throw only if the callee states onThrow.

TScert’s parser makes many of its calls through Gate’s fields (next slides), so stating an effect on one of its functions means stating it on everything it reaches that way.

Using it on TScert’s own code

More terms, for TScert’s own source

Slice and census

A slice is one top-level function of tools/ (TScert’s TypeScript front end) plus the definitions of its own file it uses, run alone through TScert; definitions of other files, such as Gate’s class, are read at their declared types. It stops at the first place TScert refuses. The census runs every slice: 488 slices, one per function of tools/, in the census run at commit 38ed032 (2026-10-24); the census at commit 6a3a864 (466 slices) predates the statements.

Gate

The class holding the state of TScert’s parser for TypeScript. Besides its data fields, its methods are of two kinds: its own, such as span, and fields holding module functions of other files, such as expr and pattern (later slides), called as gate.expr(…).

The 16 measured

16 functions of three parser files (fragment-statements.mts, fragment-expressions.mts, fragment-classes.mts): the 11 that the design document (docs/drafts/method-effects.md) names for measuring, and 5 others that WORK.md, the project’s status file, records. Each runs as a slice; the stages lowering (the parsed program to TScert’s calculus, the core language its checker reasons about), producer, search, checker and explanation (the stage that locates and explains a refusal) each may take 300 s before it counts as a timeout.

The 16: enumMembers, enumOpen, resolve, moduleFunction, inertRead, collect, inert, patternDefaults, steppedPattern, pattern, forOfPattern (these 11 verify); protocolPattern, patternStmt, neverAssigned (stopping later, “What to expect”), abrupt (refused inside the function markEarly, census of 38ed032); classBody.

The line that needs expr’s statement

pattern’s map relies on the expression parser’s statement

const props: PatternPropAst[] = node.elements.filter((el) => !el.dotDotDotToken).map((el) => {

  … return { …, target: gate.pattern(el.name, names),

    default_: el.initializer ? gate.expr(el.initializer) : null };

});

  • What it is: pattern parses a destructuring pattern, such as { a, b = f() }. For an object pattern it maps the elements other than a rest ...r (whose dotDotDotToken is set) to a PatternPropAst each, the parsed form of one property. filter’s callback calls nothing. The map’s callback (besides gate.fail, typed never, and ts.isIdentifier, not shown), whose default_ is the property’s default expression parsed, calls gate.pattern (pattern itself, on the element’s name; names collects the names bound so far) and gate.expr, the expression parser, on its default: both module functions in Gate’s fields, so the calls rely on the statements the fields’ types carry (“A field holding a module function”).
  • Reach: in the census run at commit 6a3a864, before the statements, 21 slices stop first at this map: pattern’s, forOfPattern’s (the parser of a pattern in for (const { a } of xs)), and 19 others whose slice includes pattern. With the statements, pattern’s and forOfPattern’s slices verify (census slices at 300 s, 2026-10-24), and the other 19 stop at other places (“What to expect”).
  • Cost: to keep the map’s result hole-free, pattern and expr state an effect, and so does what they reach through Gate’s fields and methods. pattern calls itself through the field gate.pattern, whose type carries pattern’s own statement: the call relies on it by the rule for calls through a field (“A field holding a module function”), which is not circular, since the function written into the field is checked against its type there. By contract closure, expr’s statement holds only if everything it reaches does: 157 of the 167 functions an untrusted syntactic scan finds state value: any, store: grow (“Statements around Gate”).

What expr’s statement needs

D-numbers: decisions of the design document

What expr’s statement rests on

  • forEachChild, TypeScript’s method calling a visitor function on each child of a syntax node, which functions expr reaches call: its contract has one signature per footprint of the table on “The footprint F” (six: value keep or any, with store keep, grow or any), taking visitors within that footprint and making the call within it, as map’s does (“Built-ins state footprints in their contracts”) (design decision D7; that it runs no code of the program but its visitors is reviewed by hand).
  • TypeScript’s type checker. The parser reads type annotations through a scope, an object of type TermScope whose function members resolve names and types and state value: any, store: grow. TScert’s reader of declaration files (.d.ts files) makes such scopes, which query TypeScript’s own type checker, distinct from TScert’s checker. Those queries are read as an audited contract, reviewed by hand: value: any, store: grow on normal return, except six that may receive an object of the program: sending it to TypeScript’s process converts it to JSON, which runs its toJSON method and getters, so these six state no effect, and a body calling one has no certified bound on its effect (design decision D8 (a)).
  • The shift calls. shift on an array the call did not allocate allows any change to stores. By design decision D5, an exception to the rule that TScert’s source is not rewritten to fit the verifier (approved 2026-10-23, WORK.md), Gate’s four shifts on its two stacks of scopes (in enterTypeParams and leaveTypeParams) are field writes, such as this.typeParamScopes = this.typeParamScopes.slice(1), unobservable since no other code holds either array; the two in closures of protocolForOf (the parser of for-of over an iterable) are reads at counters.
  • A checker rule for a method call with names or literals as arguments on a value of several shapes, such as node.getStart(file) on a Node: TScert reads and calls the method in one step, which no rule bounding a footprint admits, so a body making it has no certified bound on its effect (design document §10). Gate’s own methods make such calls (span calls node.getStart). The design document adds the rule if a measured slice is refused at such a call.
  • Statements on everything expr reaches, each certified where a verifying slice includes it, callers otherwise verified relative to it: 61 of the 183 functions expr and the parser’s TermScope reach are certified (docs/drafts/method-effects-inventory.md, 2026-10-24).
