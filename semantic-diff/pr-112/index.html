Verify a key-adding write on a module's own object, the cell read again after the right side

verified
graphemes.ts#getGraphemeRulesgraphemes.ts#findGraphemeEnds

Why

Pretext's grapheme rules are a module-level cache in the form JavaScriptCore runs fast, a record whose keys are added once:

const graphemeRules: Partial<Record<GraphemeTable, GraphemeRules>> = {} return graphemeRules[table] ?? (graphemeRules[table] = parseGraphemeRules(table))

It was refused: "a write at a key known only at run time may add the key to an object another reference holds". A key-adding write is the copy of the object with the key, rebound to every local holding it, which is JavaScript's in-place write only where those locals own the object; a module constant is read by every function. A Map (verified) makes findGraphemeEnds 74 ms against 50 ms. Extending ownership to the module needs the holder read again after every operand that may run code, and the write's value, which the key-adding lowering discarded.

Soundness

Simulation, reviewed and unproved like every lowering: JavaScript's object bound to c and the object the cell holds have the same own properties and the default prototype, and nothing but the cell reaches either, except an access's receiver for that access. A read, a key test and a write in place run no code between the receiver's read and the access. A key-adding write reads the cell again after its right side, then stores the copy of the current object with the key, which has the own properties JavaScript's [[Set]] leaves on an ordinary object at a string key other than __proto__. No admitted mention observes the copy's identity, key order or attributes. The safety of each unit is checkUnitJson_safe's, unchanged; module composition stays open.
