TScert · its own front end

What stops TScert's own code, and what lies behind it

TScert checks type claims about TypeScript programs and is run on its own front end, function by function. In the run of 2026-10-24, 178 of its 490 functions are verified. This deck ranks what stops the other 312, finds blockers hidden behind the first one with crude rewrites of the source, and lists a small reproducing file for each of the 121 blockers found. Seven large blockers are investigated: their cause, the repair, and what the repair would trust. Each blocker's cause is a pipeline case of TScert's suite, and patterns TScert rightly refuses are removed from its own code (slides “45 cases stand for the 121 repros” and “Changes to tools/”).

Words used in this deck

How TScert works, in three cards

Verified, refused

TScert verifies a function when it proves it safe: every value the function reads, writes or returns has its declared type. Otherwise it refuses the function, naming the first place it could not prove. A refusal is the location and its reason.

The four stages

A source passes through, in order: the gate, which reads the TypeScript and refuses what lies outside the language TScert admits; the producer, which proposes types for every expression; the search, which looks for a proof of them; and the checker, proved correct in the Lean proof assistant, which checks that proof. Only the gate and the checker are trusted.

Contract

TScert's reviewed description of code it does not check itself, such as a Node or TypeScript library function: written and audited by hand. A contract is an assumption the result rests on; adding one widens what TScert trusts.

Words used in this deck, continued

Slices, the census, and coverage

Slice

One top-level function of TScert's front end (the folder tools/), copied into a file of its own with the definitions of its file it uses, and run alone through TScert. A slice stops at its first refusal: whatever else it would meet stays unseen.

Census

The run of every slice: 490 slices, one per function, in the census of commit 963ffa4 (2026-10-24, each stage allowed 300 s).

Statement coverage

The share of the front end's TypeScript statements (an if, a return, an assignment …) that lie inside verified functions: 1,347 of 12,698 in that census, 10.6%.

Looking past the first refusal

crude, may change behaviour, never counted as verified

Rewrite the slice's source until it reaches the end

  • The loop: run the slice; at a refusal, apply a crude local rewrite of the slice's copy that gets past it; record the refusal as a blocker; run again; stop when the slice reaches the end, when no rule rewrites the refusal, after 12 rewrites, or after 1,200 s.
  • A diagnostic only: it is a separate tool (dev/blocker-rewrites.mts, branch blocker-rewrites, commit 90feee4) that edits copies and changes nothing TScert trusts. A rewritten slice that gets through is reported as “reaches the end after rewrites R1…Rn”, never as verified.
  • What it may change: a rewrite can alter what the code does, so a blocker found after it is one the original code may or may not meet. The order says what was exposed, not what caused it.

Blocker · 27 functions, 701 statements

investigated by hand

node:path's constant sep

  • Where: the slices of tools/family-activation.mts (21), declaration-graph.mts (5) and files.mts (1) read sep, a property of the object node:path exports.
  • Who refuses, and why: the gate. TScert reads a library module's value only through a reviewed entry, and the entries cover functions, not constants: a missing contract, not a restriction any document states (cited: SOURCE-CONTRACTS.md, “Library modules”).
  • Repair, and what it trusts: a constant entry in the reviewed list of library modules, stating sep as "/" | "\\". It adds one host assumption: nothing replaces path.sep while the program runs; Node lets code write it (observed with a Node script). Size: about 30–50 lines (estimated).
  • Behind it: rewriting sep by hand in 7 of the 27 slices (a test apart from the loop), 1 reaches the end; the others stop at Node's Buffer, crypto's hash options, and an in test ("name" in f) on a function value (observed).

Blocker · 27 + 13 functions

investigated by hand

Node's Buffer, and crypto's hash

  • Where: most of tools/files.mts: Buffer.compare in one sorting helper, the fs functions statSync, mkdirSync and chmodSync, whose path parameter admits a Buffer, written Buffer and Dirent types, and createHash.
  • Who refuses, and why: the gate, rightly: an unlisted Node function is read as its declaration states, and Buffer's declaration is outside what TScert reads (its parent type Uint8Array is refused by itself; Buffer has about 100 members, some running caller code) (observed and cited).
  • Repair, and what it trusts: new reviewed entries: the fs functions at string paths, createHash with update and digest, and a Buffer type with a closed list of the members the code uses. They add host assumptions, statements about Node that TScert does not check: Buffers keep their standard methods, hashing runs no caller code, each to audit against Node's source. Reading files as text instead would change what the hashing computes.
  • Behind it: Dirent, the TextDecoder global, a read of splice on a value that may be an array or a record, and Readonly (observed).

Blocker · 21 functions, 654 statements

investigated by hand

Object.entries at two kinds of overload

  • Where: every one waits on one helper of tools/type-term.mts, sameData, which calls Object.entries twice: once on a value narrowed to an array, where TypeScript picks the generic overload, once on an object, where it picks the plain one.
  • Who refuses, and why: the gate, refusing one member used at a generic and a plain overload. SOURCE-CONTRACTS.md states the refusal (“a generic, optional or modified method … [is] refused”) without saying what behaviour it excludes; its cause is how TScert translates a library member for the checker, from plain signatures or from one generic signature, never both (cited).
  • Repair, and what it trusts: let a member carry both kinds: small, no new trust (estimated).
  • Behind it: sameData stays refused: its parameters are typed unknown, an array fails the generic overload's parameter, the plain overload excludes values made by the compiler, which TScert keeps opaque (a stated restriction), and a callback is typed any (observed). Passing it would need stated parameter types, a change to TScert's source under its rules for such changes (estimated).

Blocker · 17 + 7 functions

investigated by hand

The sync API's API class

  • Where: functions using the class API of TypeScript's synchronous compiler interface (the sync API), through which TScert's front end asks TypeScript about a program. It is declared class API<FromLSP extends boolean = false>: 17 functions use it as a type (14 of them meet this first), 7 in compiler-channel.mts import it as a value.
  • Who refuses, and why: the gate, twice. (a) TScert reads a conditional type (X extends Y ? A : B) only once its type parameters are known, and its reviewed list of the class's members states updateSnapshot with the parameter type FromLSP extends true ? … : …, read for the class in general, never at API<false>: no program can use API as a type, a defect of the reviewed list (observed: even a function only calling api.close() is refused). (b) TScert does not admit constructing API (new API(…)), a stated restriction, and refuses a value import of it even where the code only uses it as a type (cited).
  • Repair, and what it trusts: (a) read such a class at each use, with its type parameters known, as TScert already reads a type alias holding a conditional type: no new trust (estimated). (b) read a value import as a value only where the code constructs it: 5 of the 7 then meet (a) (estimated).
  • Behind it: Object.getPrototypeOf outside the reviewed globals, members outside the reviewed views, and Parameters<API["updateSnapshot"]> (observed in part).

Blocker · 20 functions of fragment-statements.mts

investigated by hand

An empty array written into a field

  • Where: the write gate.hoisted = [] in the function hoisting, which every one of these slices includes (gate here names the parser's state object, not the stage).
  • Who refuses, and why: the search refuses, rightly; the cause is a defect of the producer. The producer proposes the new array [] by itself, as an array of nothing, instead of at the field's type Stmt[] (a write to a local variable already gets the expected type, a write to a field does not), and the search finds no proof: an array's elements are a cell other references may share, so an array of nothing is no Stmt[] (cited: the write rule in Lean).
  • Repair, and what it trusts: pass the field's type to the written value, for field and index writes: about 5–10 lines of the producer, no Lean change, no new trust, since every write is still checked (estimated).
  • Behind it: the same cause at gate.hoist = {…} one line up; then, in forInStmt, a call gate.local(d.name) after a narrowing, cause not established (observed).

Blocker · 20 functions, 3,091 statements

investigated by hand

Compiler-API members outside the reviewed views

  • Where: reads of 7 members of TypeScript's compiler API that TScert's reviewed list for each class (a view) leaves out: Type.isUnionType (10 functions), Checker.getContextualType (4), API.parseConfigFile (2) and four others.
  • Who refuses, and why: the gate, rightly: a member outside its view is a located refusal until it is reviewed (cited: COMPILER-API.md, reading rule 4). Five are omissions, four of them members the front end began to read after the views were written; the two this-is-X guards, such as isUnionType(): this is UnionType, are left out on purpose.
  • Repair, and what it trusts: the five: one reviewed entry each, its implementation audited. The guards used only as a test: read without their promise, no new trust. Using what the guard promises, as computed-types.mts does with getTypes() after isUnionType, needs stated type guards, a large design already listed in TScert's status file.
  • Behind it: the next members outside the views (isTypeParameter, Snapshot.dispose, isStringLiteralType) (observed).

Blocker · 29 functions, 1,087 statements

investigated by hand

Readonly over a record

  • Where: Readonly<Record<K, V>> in tools/array-prototype.mts and guard-closure.mts, reached by their importers. Readonly<T> is the mapped type { readonly [P in keyof T]: T[P] }.
  • Who refuses, and why: the gate's reader of types, which reads a mapped type's value once and so refuses a value naming its key, as T[P] names P. SOURCE-CONTRACTS.md states the refusal but no behaviour it excludes (cited); that it is a limit of the reader only is estimated.
  • Repair, and what it trusts: read such a mapped type key by key, each field taking T's member type: in the trusted gate, no new contract, about 50–120 lines with a formal rule (estimated). The same rule reads Pick over known keys.
  • Behind it: rewriting Readonly by hand in 13 of the slices (a test apart from the loop), 3 reach the end; the others stop at import.meta, a local class extending Error, the sync API's conditional type, Object.hasOwn and one search refusal (observed).

  • A case is a source with its expected outcome: the suite checks each blocker is still refused exactly so, and reports it when a fix makes it verify or moves its refusal. Run them alone with make cases P=blocker-.
  • Gap or negative: a refusal blocked by a missing rule or contract is a gap; a negative only where the refused behaviour is a principled restriction or an unsafe program.
  • A negative in TScert's own code cannot stay: a pattern rightly refused in a small file is rightly refused in tools/ too. So each negative's pattern was removed from tools/ wherever it occurs (next slide).

Limits, and the next round

The catalogue of rewrites decides how far the loop sees

  • What the loop cannot see: the obligations inside what a rewrite removed (64 original statements in this run, measured), and refusals with no rule: a refusal where branches meet, or about what memory holds, has no local rewrite.
  • Where it stops: 295 of 312 functions at a refusal no rule rewrites (measured). Each new rule lets the loop look past one more kind, and adds the repros it then finds.
  • The next phase: grow the catalogue and rerun, turning every new blocker into a case; the gap cases are worked on one at a time with make cases P=blocker-, and the census measures the effect from time to time.
  • Conjecture: coverage with holes grows faster than verified coverage as rules are added, and the families that most often appear after rewrites gain weight in the ranking: library globals, Readonly and crypto; the most frequent, the callback parameter typed any (21 functions), is a pattern removed from tools/ (slide “Changes to tools/”).
