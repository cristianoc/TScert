TScert · run time of one census slice

Where lowerFile's 239 seconds go

TScert checks type claims about TypeScript programs and is run on its own front end, one function at a time. Checking the function lowerFile of tools/fragment-parse.mts took 239 s, with no earlier result to reuse. This deck attributes that time to the steps of the check and, inside the slowest one, to what it repeats. Two repairs of data structures, which change no output, bring the check to 108 s. Of those, about 30 s follow the size of the program; of the producer's remaining 64 s, 30 s are measured repetition, and three designs are proposed for it. The next slide explains the words.

Words used in this deck

A slice, its stages, and its outcome

Slice, census, refusal

A slice is one top-level function of TScert's front end (the folder tools/), copied into a file of its own with the definitions of its file it uses, and checked alone. The census checks every slice and records each one's outcome and the time of every step. A check ends verified, or in a refusal: the place where no proof of the proposed types was found, and why.

Stages

A check runs separate programs, one after another. parse: TypeScript's compiler reads the slice and each module it imports into syntax documents. lower: Lean, a proof assistant, derives each function's control-flow graph. propose: an OCaml program, the producer, proposes a type, a claim, for every expression. plan: Lean decides which certified imports (slide “Import rounds”) the slice may use. search: Lean looks for a proof of the claims.

Empty store

A cache keyed by a stage's exact inputs replays a stage it already holds. Every measurement here starts with it empty, so every stage runs. Times are of one check on a 12-core laptop, at commit ee0ed0e5 of the repository unless a slide says otherwise.

  • How the producer types a function: in one pass it walks the function's control-flow graph, carrying an environment from node to node. Where two paths meet, such as the two arms of a conditional expression c ? a : b, it joins their environments: each binding of one path's environment is looked up by name in the other's, and the two types are united.

Measured: sampling profiler, and a build counting each lookup

93% of the slice's proposal is looking up names in lists

  • Sampled: 1 ms samples of the running proposal: 93% inside OCaml's List.assoc_opt, the standard lookup in a list of pairs, almost all of it comparing names.
  • Counted: the join's lookups (the two shown, and two more in the join and the function calling it) ran 34.2 million times each and visited 3.7 to 3.8 billion list cells each: about 110 cells per lookup.
  • Why: an environment is a list, so a lookup walks it, and a join makes ≈100 such walks where a table answers each lookup directly.

Two repairs, changing no output

The same claims; the slice's proposal in a quarter of the time

1 · A table for the join

Each environment of a join is indexed once by name (a hash table keeping the first binding of each name, which is what the list lookup finds), and every binding is looked up there. The joined environment is the same list, in the same order.

2 · Uniting sorted lists by merging

A type is often a list of alternatives kept sorted without repeats. Uniting two such lists sorted their concatenation again; it now merges them in one pass when both are sorted, and sorts otherwise. The result is the same list.

Measured: census of ee0ed0e5, empty store

Import rounds: one import dropped per round

  • Certified imports: the slice may type a call of an imported function by what TScert proves of that function in its own module, instead of by its declared type alone. It may do so only where the slice and the module give the function the same signature. Before proposing the slice, the plan checks each such import; where it refuses one, the import is dropped, and the round starts again.
  • This slice: 14 rounds each drop one import; the 15th plan passes, the slice is proposed, and the search stage runs the plan once more to divide its work: 16 plans of 0.6–0.9 s, 11.0 s. Each plan reads the whole 30 MB syntax document.
  • Modules proposed again: a module's proposal depends on which of its own calls of other modules are still typed by certified imports, so a dropped import can change it; each round proposes again each module so changed: 27 proposals of 21 modules, tools/declaration-graph.mts five times at 1.8 s.
  • Avoidable: a plan that reports every import it refuses lets one round drop them all: an estimated 16 → 3 plans (−9 s), and about −5.5 s of the 8.8 s of repeated module proposals, since each changed module is still proposed once more. The outcome stays the same only if no refusal depends on another import being dropped, which the change would have to show.

Proposed, not built

Three designs for the producer, by expected gain

  • Entry environments in one evaluation: evaluate a statement once while typing it, in evaluation order, handing each sub-expression the environment the evaluation has reached. A rerun sees the claims typed so far, so the design must show it gives the environments the reruns give, or record the claims each step reads and rerun only when one changed. Expected: one evaluation per statement instead of 27 in the slice; estimated −18 s in the slice and −11 s in the four modules measured.
  • Passes only where an assumption changed: type the functions callee before caller, in the order of the call graph, so a function is typed once its callees' effects are final; a recursive group is iterated alone. Expected: lowerFile typed in one effect round, 4 → 2 passes, an estimated −3.5 s once the first design lands; the closure pass stays.
  • Shared, numbered types: build each distinct type once and give it a number, so two types are equal exactly when their numbers are; union, join and lookup then compare numbers. Expected gain not measured; the largest change of the three, touching every module of the producer.
  • With the first two and one import round, the producer's 64 s of CPU in this check would fall to an estimated 25 s, before the third; with the plans saved too, the check would take about 60 s, the compiler's 20 s and the search among them.
