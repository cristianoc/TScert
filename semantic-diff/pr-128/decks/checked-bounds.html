TScert · checked array bounds

Proving array bounds in TypeScript

TScert checks safety claims about TypeScript programs. Integer linear arithmetic relates indices to array lengths. An untrusted producer proposes types and loop invariants; untrusted proof search constructs certificates; a checker proved sound in Lean validates them. Source translation and library contracts remain trusted. The case study is pretext, a text-layout library: which array-bound checks can verification discharge, and which proof obligations remain?

The obligation

number[] and number do not establish a bound

function at(xs: number[], i: number): number {
  return xs[i]!
}
 
at([10, 20, 30], 1)    // 20
at([10, 20, 30], 3)    // undefined
at([10, 20, 30], 1.5)  // undefined

  • Assertion: ! removes undefined from the static type; it performs no run-time check.
  • Proof obligation: i is a safe integer and 0 ≤ i < xs.length, under an array contract that makes the element present.
  • Case study: pretext’s checked rewrite, verified by TScert, turns each bound into a run-time check: 376 checked reads, 55 guarded writes, 70 explicit undefined checks.
  • Experiment: replace those checks with assertions and contracts, and measure what verifies.

Arithmetic model

the rules proved against Lean’s model of IEEE doubles

Integer reasoning over exact JavaScript arithmetic

Σᵢ cᵢ·tᵢ ≤ d

Σᵢ cᵢ·tᵢ ≠ d

(cᵢ, d integers)

  • Safe integers: a numeric term denotes an integer only within ±(2⁵³ − 1). Fractions, infinities and NaN denote nothing, so no fact about them holds.
  • Exact addition: r = a + b holds when the operands are safe integers and the known facts bound the sum within that range; there the double sum is exact.
  • Terms: values, field paths p.f.g, array lengths (at most 2³² − 1) and typed-array lengths. A term is partial: where its path meets no object, it denotes nothing.
  • Branch facts: on safe integers < and === are integer order and equality: the true branch of i < n gives i ≤ n − 1, the false branch n ≤ i.

  • Proof search: untrusted search constructs certificates for the proposed claims.
  • Checking: the checker validates initialization and preservation on every incoming edge.
  • Arithmetic: certificates use nonnegative linear combinations, integer rounding and disequalities; search uses Fourier–Motzkin elimination.

Function contracts

schematic, after pretext’s classifySegmentUnit · the call rule proved

Callers establish the precondition

/** @requires safeInteger(i) && 0 <= i && i + 1 < breaks.length */
function nextFlag(breaks: Uint8Array, i: number): number {
  return breaks[i + 1]!
}

  • Body: verification assumes the precondition and proves the read in bounds.
  • Analyzed callers: each call must establish the precondition of its evaluated arguments; a call that cannot is unverified.
  • Clause language: conjunctions of safeInteger and linear comparisons over parameters, field paths and lengths, optionally under null guards p.f === null || …. A clause runs no code.
  • Trusted boundary: callers outside the analyzed sources are trusted to meet exported preconditions.

Contract support

C is a clause of the shared language

Preconditions, postconditions and invariants

ContractSupport
Preconditionwritten as @requires C; checked at analyzed calls, assumed by the body
Postconditionpartial: result facts from native specifications and type invariants; no written postcondition syntax
Type invariantwritten as @invariant C on a type; obligations at function boundaries
Loop invariantwritten as @invariant C before a loop, or inferred; checked on every edge into the head

Clauses are linear relations over values, field paths and lengths, under null guards, and quantified clauses forall i in xs: B over an array’s elements. A heap change preserves no quantified fact: a stated limit.

Type invariants

an opaque-type regression example, after pretext’s handle · the boundary rules proved

Type invariants become preconditions and postconditions

/** @invariant this.segmentFlags.length
 *     === this.widths.length
 *  @representation PreparedLineBreakData */
export type PreparedText = {
  readonly [preparedTextBrand]: true
}

  • Representation invariant: PreparedText is opaque; @representation names its underlying record. The invariant equates two array lengths.
  • Precondition: for a parameter without a default argument, callers establish the invariant and the body assumes it.
  • Postcondition: every normal return establishes result invariants and restores those of parameters never reassigned.
  • Casts: a cast checks the representation type; the invariant needs proof at a call or return.
  • Preservation: across calls, keeping the equality needs a frame condition that protects the field references and the lengths.

Frame conditions

the preservation rules proved

Mutations preserve facts through checked effects

A fact over the heap reads particular locations. TScert’s footprint mechanism, its frame conditions, checks whether an operation leaves those locations unchanged, or changes them in a way that preserves the inequality.

OperationPreservation
Write a numeric fieldarray lengths preserved; facts about that field restated from the written value
Write xs[k] below the lengththe length preserved
out.push(v)lower bounds on out.length preserved; upper bounds dropped
Call with a checked frame conditionfacts whose locations its frame protects
Any stepa typed array’s length: fixed for its life (trusted)

These rules concern normal returns; a throw carries a frame condition only where one is stated for it.

Soundness and trust

a conditional safety theorem proved · explicit assumptions trusted

What certificate acceptance guarantees

The Lean theorem connects acceptance to modeled safety for every function in the checked unit, assuming input types, preconditions, separation requirements and environment contracts. Normal returns satisfy the checked postconditions. Exceptions and divergence are permitted.

  • Untrusted inference: the producer proposes types and loop invariants.
  • Untrusted proof search: search constructs certificates from the proposed claims; the checker validates them.
  • Trusted computing base: source and annotation translation; correspondence with JavaScript; Lean’s kernel, compiler and executed checker.
  • Environment assumptions: native contracts; standard-object behavior; external callers satisfying exported contracts; typed arrays backed by fixed-size buffers that are never detached.

The takeaway

Contracts state the obligations at boundaries; certificates discharge them; frame conditions carry facts between.

Where the checker accepts, a bound check becomes a proof, under the trust the deck states. Where no annotation can make code safe, the analysis reports the site.
