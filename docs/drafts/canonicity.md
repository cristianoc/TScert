# Draft: canonical representations

A design written against TScert main at d578dd8; its progress is
[WORK.md's](../../WORK.md#status).

This draft defines the property, names the places where it must hold, states
what each place requires, and how the property is enforced and kept under
extension. The representation each place adopts to meet its requirements is
designed in a draft of its own (§6).

**Evidence labels.** **Measured** gives the command, the commit and the date.
**Cited** names inspected code. **Proved** names a Lean theorem.
**Conjectured** marks a design claim, a proof obligation or an estimate.

## 1. The property

### 1.1 What a place fixes

A representation is a data type whose values stand for something: a set of
values, a type, what holds of the heap at a program point. A **place** (§3)
is a representation at a point of the pipeline where it is accumulated or
used as a key, and it fixes:

- **contexts** $`\Gamma`$, what the meaning is relative to, restricted to
  the part its decision procedure reads (for heap facts, the finite
  primitive predicates a slot's type denotes, where that is defined; for
  search types, the inclusion certificates the evidence carries);
- **raw values** $`R`$, everything the place's operations produce;
- **stored values** $`S_\Gamma \subseteq R`$, those it keeps, keys or writes;
- **a meaning** $`⟦r⟧_\Gamma`$ of each raw value;
- **laws**: a finite list of rewrites, each preserving the meaning under
  $`\Gamma`$ (proved in Lean for Lean's places, tested for the others,
  §5), generating an equivalence $`\approx_\Gamma`$ on $`R`$;
- **a normalizer** $`\mathsf{norm}_\Gamma : R \to R`$ whose results are
  stored values and which decides $`\approx_\Gamma`$ by comparing results;
- **consumers**: the operations that read its values by meaning (checks,
  merges, key lookups), distinct from **validators**, which read a value's
  representation (a decoder checking that a value is in normal form).

Every equivalence is generated by laws. Equality of meaning is not used as
the equivalence: relative to a type, it asks whether that type is empty (an
empty value set and `[defined, undef]` mean the same under a type with no
values), and types empty in meaning need not compare equal to the empty
type ([POSITIVE-TYPES](../POSITIVE-TYPES.md) states this incompleteness). A
law that rests on an inclusion between types applies where the context
holds a certificate for that inclusion; the normalizer does not search for
one, and the certificates belong to the context, so extending them changes
the context.

### 1.2 Contextual canonicity

A place is **canonical** when its stored values are unique per class:

```math
\forall\, \Gamma.\ \forall\, s_1, s_2 \in S_\Gamma.\quad s_1 \approx_\Gamma s_2 \implies s_1 = s_2
```

and every value it stores, keys or writes is in $`S_\Gamma`$ for the context
of its use.

### 1.3 What it gives, and what it does not

Canonicity gives **path independence**: what is stored for a class is a
function of the class, not of the tests, reads, calls or merges that
produced it, and equality, hashing, memo tables, interning and
deduplication on stored values decide $`\approx_\Gamma`$. It gives no size
bound: a normal form can be large, and successive points hold successive
classes. Bounds are stated separately (§4).

## 2. The case that shows it

**Measured** (deep dive
[One condition, 300 MB of evidence](../deep-dives/knowledge-growth/deck.mts),
2026-10-27). Lean's heap knowledge stores, after a failed test
`node.kind === k`, a new fact beside the earlier facts on the same field
(lists of 99, 98 and 97 values where the last suffices), one copy of each
fact on every slot holding the same object, and each fact as the full list
of values it leaves. A condition of $`n`$ tests on one field stores values
growing as about $`n^3`$ times the type's size: 4, 8 and 16 tests store
95,646, 762,992 and 6,219,164 values without the rule `call-keep` (branch
`gap-in-unknown`, b6a0dc93). That rule (a7b7843) lets heap facts survive
calls that change no location. The census slice of `moduleFunction`
(`tools/fragment-expressions.mts`) includes, among the functions it calls,
`resolve`, whose visitor tests eleven compiler-API guards in one condition;
the slice's evidence is 4.9 MB without the rule and 300.7 MB with it.

## 3. The places

Each place states its representation, its context, its consumers, the forms
one class takes today, and its **requirements**: the forms its laws must
identify. **Cited** at d578dd8; *conjectured* marks what was inferred from
the code and not traced end to end.

### 3.1 Lean: heap knowledge

**V · Value sets.** A fact's contents, `List Atom`
([HeapFacts.lean](../../lean/Verification/Semantics/HeapFacts.lean));
meaning: one of the atoms holds of the value. Context: the slot type's
primitive predicates. Today: a member another covers (`[numLit 3, num]`),
a tag atom beside its primitive (`.tag isNul false` and `nonNull`), order,
duplicates. Requirements: identify those forms; express a conjunction of
exclusions (“not `a`” and “not `b`” on a string field) as one value set,
which no finite list of atoms does; keep the meaning of a tag atom,
including that both answers of a tag can hold where the prototype decides
it (`Atom.holds` with `protoFree` false).

**K · Facts.** `Facts := List Fact`, cell facts and value facts
([HeapFacts.lean](../../lean/Verification/Semantics/HeapFacts.lean),
[HeapKnowledge.lean](../../lean/Verification/Semantics/HeapKnowledge.lean));
meaning: every fact holds; a cell fact also states that the read it
constrains exists. Accumulated at every program point (`observeTyped`,
`withTypedLinks`, `copyFacts`, `writeOutput`, `project`), merged by `meet`.
Today: several facts on one slot and field, one per alias, a fact the slot
type implies, order, and a value fact's `field`, which `ValueHolds`
ignores. Requirements: identify those forms, keeping cell facts and value
facts apart, and removing a fact only where the context also establishes
what the fact states besides its contents.

**L · Links.** `Links` ([HeapLinks.lean](../../lean/Verification/Semantics/HeapLinks.lean)):
alias links and read links, a read link naming its receiver slot, its
field, the slot holding the value read, and whether the read may find no
field. A read adds a link for every alias of its receiver; `project` adds an
alias link for every pair of a group. Today: an alias's orientation, an
alias implied by two others, a read link on every alias of its receiver,
order. `HeapLinks.check` compares a target link with the source links up to
the source's alias classes after mapping (`classes`, `rep`), so these forms
differ in storage alone ([LinkControls.lean](../../lean/Verification/Tests/LinkControls.lean)).
Requirements: identify those forms, and an alias link's `field` and
`optional`, which `HeapLinks.Holds` ignores; keep each read's destination
slot (two reads of `x.f` into two slots stay two reads, or their
destinations become aliases by a law).

**S · Separation.** `Separation`
([HeapSeparation.lean](../../lean/Verification/Semantics/HeapSeparation.lean));
meaning: which locations differ. Today: a pair stated from either side, one
fact over two fields and two facts of one field each, whole-object and
per-field forms over the keys a slot's type admits, depth after `rebase`,
order and duplicates. Requirements: identify the forms a pair takes on the
slots of one alias class, group a subject's pairs into one fact and merge a
partner's fields, with a bound on the facts; whole-object and per-field
forms stay distinct, since a key bound does not make them equivalent where
a field list may hold a key twice, and grouping is not unique, so S has no
uniqueness requirement
([heap knowledge, §5](heap-knowledge-canonical.md#5-s-separation)).

**K, the whole:** `Knowledge`, the four above; meaning
`HeapKnowledge.Holds`. Consumers: `check` and `meet`; the evidence
encoder, which interns it by the JSON text of its facts; `==` for promise
yields (`CertificateProducer.lean`) and cuts (`SourceRequests.lean`).

### 3.2 Lean: types, observations, evidence

**T · Search types.** `Ty ι = List ι`, a union of labels
(`Programs/TypingBasics.lean`); meaning `PositiveRules.meaning`. Built by
search (`tagSlice`, `refineBy`, `memberSlice`, `meetImplications`) and keys
of its tables (`subtypes`, `summaryAnswers`, `fieldSlices`, `proved`,
`KnownIndex`, `sliceTable`, the family tables, the evidence's types table).
Types decoded from the source are sorted and duplicate-free, which the wire
validator checks (`Source/Claims/Wire.lean`); types search builds are not
re-sorted (*conjectured*: the same set in another order misses a table).
Requirements: permutation and duplication; a label covered by another
where the context certifies the inclusion, with one representative chosen
among labels that cover each other; stored keys normalized again when the
certificates in the context grow, or keyed with the certificates they were
normalized under.

**E · Equation clauses, trees and heads.** `Clause`
([PositiveNormalization.lean](../../lean/Verification/Types/PositiveNormalization.lean)),
`Tree`/`Union` (`Types/EquationGraphs.lean`) and head interning
([Interning.lean](../../lean/Verification/Source/Equations/Interning.lean)).
Unions are sorted and deduplicated (`normUnion`, `canonMeet`, `canonNums`,
`canonStrs`); a head's key is the spelling of its clauses (`internKey`). A
clause holds accumulated collections: record operands, field lists,
optional fields, methods, key bounds, stable keys, index contracts,
signature lists and tuple contracts. A meet of two record clauses
concatenates them (`PositiveNormalization.lean`); the meaning of stable keys
(`stableKeysT`, `Types/Types.lean`) ignores order and duplicates, so
`[a, b]` and `[b, a, a]` spell two heads of one meaning. Requirements: for
each collection, the order and duplication its meaning ignores, keeping
distinct constraints that share a key; `bool` and
`[boolLit true, boolLit false]`; T's laws for unions.

**B · Key bounds.** `KeyBound`
([Types.lean](../../lean/Verification/Types/Types.lean)): a bound that
allows only its keys or excludes them; meaning `KeyBound.admits`, and a
list of bounds means all of them. Requirements: order and duplication of
keys; several bounds on one object, allowing and excluding, as one.

**O · Observations and tags.** `Tag` (`Semantics/Calculus.lean`) and
`Observation` (`Programs/BranchRefinement.lean`), in the keys of the slice
tables. Requirements: `numEq` at $`+0`$ and $`-0`$; NaN bit patterns; a
truthiness test on a slot whose context is Boolean and the Boolean test;
the order and duplicates of tag lists.

**I · Implications and yields.** `Implication`, `Yield`
(`Programs/PromiseCalls.lean`), carried along edges and compared by type
equality; an implication is repeated on every alias slot. Requirements:
T's laws for their types; the order and duplication of implication and
yield lists, which `ImpliesOk` and `YieldsOk` quantify over; an implication
stated once per alias class.

**X · Evidence documents.** The interned tables of the evidence
(`Interned`, [EvidenceWire.lean](../../lean/Verification/Source/EvidenceWire.lean)):
types, contexts, links, separations, value sets, knowledge, proofs, numbered in order
of first encounter. Meaning of a document: the tree its roots unfold to,
so that two identical entries and one shared entry mean the same.
Requirements (canonical serialization): only entries reachable from the
roots, identical entries shared, numbering deterministic and respecting
dependencies (a proof's premises precede it, as the decoder requires),
the traversal left to X's design; a knowledge entry shared by points of different
contexts checked at each use under that use's context, as `check` does
today; proof entries shared, not one proof per proposition.

### 3.3 Producer

**P · Producer types.** `Semantic.ty` (`ocaml-producer/semantic.ml`).
Joined at every merge (`union`, `widen`, `join_env`, `merge`), and the
fixpoint ends when a state equals the previous one (`flow.ml`). `union`
sorts and deduplicates atoms (`ground`) and keeps members another covers:
`union (Atoms [Num]) (Atoms [NumLit 1])` is `Atoms [Num; NumLit 1]`.
Requirements: permutation and duplication; a literal beside its base kind;
atoms split across a union's arms; a meet's operand order; record field
order. A named type beside its expansion stays two forms (their equality is
a type question).

**N · Narrowing facts.** The environment's field and path facts
(`ocaml-producer/environment.ml`), keyed by name and field. A truthiness
test on `x.f` writes the same field under a field key and a path key
(`refinement.ml`), and `fact` keeps a knowable fact equal to its contract,
as a join does. Requirements: a field fact and the path fact of length one;
a fact equal to its contract.

**M · Flow metadata.** The analysis state's lists
([analysis_state.ml](../../ocaml-producer/analysis_state.ml)):
`record_growth`, `mark_exact_local`, `record_holder` and
`mark_exact_allocations` prepend entries, so a repeated mark makes a state
of a different spelling with the same content. At joins
(`proposal_flow.ml`), `grown_locals` and `exact_allocs` are sorted and
deduplicated, and `exact_locals` and `holders` are intersected keeping the
left operand's order. The fixpoint compares whole states; that the
repetitions delay its convergence is *conjectured*, with no trace or case
showing it. Requirements: the lists as sets.

**Q · Producer declaration memo.** `definitions`
([type_queries.ml](../../ocaml-producer/type_queries.ml)), keyed by the
declaration and its arguments `(id, args)`. Requirements: P's, on the
arguments.

**W · Claims wire.** Labels and rows (`ocaml-producer/claims.ml`), decoded
by Lean. Label lists are sorted and deduplicated, two or more literals of a
primitive become a sorted set, and Lean's validator checks the order.
Requirements: T's laws on labels; a meet's operand order; a symbolic union
flattened; a record row's field order.

### 3.4 Front end

**F · Type terms.** `TypeTerm` (`tools/declaration-types.mts`), compared by
`sameTerm` (`tools/type-term.mts`) and the deduplications of overloads and family members. Unions are in
source order with no flattening or deduplication, `optionalTerm` wraps
`T | undefined` again as `(T | undefined) | undefined`, and fields follow
the order of the key union a mapped type expands. An optional field and a
required field admitting `undefined` differ in meaning (presence), and the
lowering keeps them apart (`Source/Equations/Core.lean`). Requirements:
union flattening, permutation and duplication; record field order; spans
excluded from comparison.

**D · Declaration instances.** `instanceOf` (`tools/declaration-graph.mts`)
keys an instance of a declaration whose computed members read its
parameters by the declaration and its arguments' data (`termText`,
`tools/named-record.mts`, the text `sameTerm` compares), which leaves out the
spans of the occurrence and keeps a declaration identity's span. Each
reference keeps its occurrence's span as provenance. Occurrences of one
declaration at the same arguments are one instance
(`computed-member-repeated`). Requirements: F's, on the arguments.

### 3.5 Stage store

**C · Stage keys.** A stage's key is the exact identity of its invocation:
its executable, its arguments, the digests of its input documents' bytes
(`pipeline/stage-execution.mts`, which sorts object keys and keeps array
order), and for an observed stage its observations, which the front end
deduplicates and sorts (`tools/files.mts`). It stays exact: inputs of one
type meaning can produce different results (a moved annotation changes the
spans of diagnostics). Canonical production upstream improves reuse
without changing the key.

### 3.6 Not a violation, or not requiring it

- **Alias holders in the producer:** after an object grows, each name
  holding it is bound to the same immutable value
  (`statement_analysis.ml`); one shared value is one representation.
- **Footprints:** the change lattice and the closed footprint grid have one
  value per meaning; the decoder rejects `grow` for the value component
  (`Source/EffectJson.lean`).
- **Syntax identities:** spans, flow-graph node ids. They identify syntax.
- **Written applications:** per-site obligations; they grow with the sites,
  which is their meaning.

## 4. Resource bounds

Separate from canonicity, each place's design states the bounds its
representation meets:

- **Units:** slots, fields, literals, tags, links, separation pairs, and
  serialized payload bytes (contexts, proofs, identifiers and literal
  lengths included).
- **Per point:** the size of a stored value in those units.
- **Per document:** for named workloads, each a family of generated programs
  with the contexts its points retain, the exponent $`e`$ such that doubling
  the repetitions multiplies the evidence by at most about $`2^e`$, derived
  from the representation or measured.
- **Normalization work:** stated per place, with its policy when a limit
  is reached. E's can be exponential: normalization distributes a
  conjunction over clauses with no growth control
  ([POSITIVE-TYPES](../POSITIVE-TYPES.md) states the limit), so E's design
  states its resource policy and what happens on exhaustion.

The baseline is **measured** (§2): a disjunction of $`n`$ equality tests on
one field, an exponent of about 3 today.

## 5. Enforcement

Five kinds of guarantee, kept apart.

### 5.1 Proved: Lean (V, K, L, S, T, E, B, O, I, X)

For each place:

```math
\begin{aligned}
&\textsf{laws}: && r_1 \approx_\Gamma r_2 \implies ⟦r_1⟧_\Gamma = ⟦r_2⟧_\Gamma\\
&\textsf{normalize}: && \mathsf{norm}_\Gamma\ r \approx_\Gamma r\\
&\textsf{stored}: && \mathsf{norm}_\Gamma\ r \in S_\Gamma\\
&\textsf{unique}: && s_1, s_2 \in S_\Gamma \land s_1 \approx_\Gamma s_2 \implies s_1 = s_2
\end{aligned}
```

`laws` and `normalize` give that normalizing preserves the meaning, which
excludes a normalizer discarding information. From the four follow the
normalizer's idempotence and
$`r_1 \approx_\Gamma r_2 \iff \mathsf{norm}_\Gamma\ r_1 = \mathsf{norm}_\Gamma\ r_2`$.

- **Storage.** Every storage, key and encoding boundary takes the subtype
  $`\{ r \mid r \in S_\Gamma \}`$ at its use's context: a stored value is
  canonical, whichever operation built it.
- **Consumers.** A consumer reading raw values by meaning satisfies
  $`r_1 \approx_\Gamma r_2 \implies c\ r_1 \approx' c\ r_2`$, with
  $`\approx'`$ the equivalence of its output (equality for a Boolean
  check); one reading only stored values satisfies it by `unique`.
  Validators are exempt: they read the representation.
- **Context changes.** An operation from $`\Gamma`$ to $`\Gamma'`$ keeps its
  existing soundness theorem (what it establishes of the meaning), and its
  output is normalized under $`\Gamma'`$ before it is stored.

### 5.2 Encapsulated: producer (P, N, M, Q)

Each representation is an abstract (or `private`) type in its `.mli`, with
constructors that return the normal form. This restricts construction to
the module; that the normal form identifies equivalent values and keeps
their meaning is tested (§5.5).

### 5.3 Checked at the boundary: wire into Lean (W, X)

Lean's decoder, a validator, refuses a value not in normal form, with its
location. This checks what arrives; it does not prove the producer
complete, and the producer's work before the document is written is not
bounded by it.

### 5.4 Audited: front end (F, D)

A branded type whose brand the normalizing constructor attaches.
`tools/unchecked.mts` accepts an assertion that states its reason, so a
brand can be asserted elsewhere; each such assertion appears in its report
and is reviewed.

### 5.5 Tested: every place and every extension

- **Laws.** For each place, a control builds, for each law, a pair of raw
  values it relates, within one constructor and across constructors, and
  requires one normal form.
- **Preservation**, for places whose laws are not proved (P, N, M, Q, F,
  D): the control also builds values of different meaning that the
  normalizer must keep apart, and checks, for each raw value, that its normal
  form admits the same sample values (a normalizer returning `top` for every
  input fails it).
- **A new constructor** fails the exhaustive match of its normalizer: in
  Lean by construction, in OCaml by warning 8 (an error in
  `ocaml-producer/dune` today), in TypeScript by a switch ending in `never`.
- **A new field** on an existing constructor is caught by a pattern that
  names every field:
  - Lean: a structure pattern omitting a field is refused, also for a field
    with a default.
  - OCaml: a record pattern omitting a field raises warning 9, a warning
    only under today's flags (`-warn-error -a+8`); the normalizers' modules
    make warning 9 an error, and their patterns do not end in `; _`.
  - TypeScript: the normalizer destructures every field and checks the rest
    is empty, `const { a, b, ...rest } = x; rest satisfies Record<PropertyKey, never>`.

  Naming a field is not handling it: each field is passed to its own
  normalizer or listed as kept as is, with the reason, so that adding a field
  requires a stated decision.
- **Probes** of these gates, one per language: a fixture whose normalizer
  misses a field or a constructor, which must fail to compile under the
  repository's own compilers (TypeScript 7.0.2), checked by the compiler's
  exit status, run as a suite of `test-all.sh` beside
  `tests/unchecked-broken/`.
- **Scaling.** Each place design's workloads (§4) at 4, 8, 16 and 32
  repetitions, checked against their exponents.

## 6. Place designs

Each place adopts a representation meeting its requirements in a design of
its own, reviewed before it is implemented:

1. **Heap knowledge: V, K, L and S**, together, since their normal forms
   depend on one another (L's alias classes name the slots K and S state
   facts on) and they hold the measured growth:
   [heap-knowledge-canonical.md](heap-knowledge-canonical.md).
2. The others, each when it is taken up: T, E, B, O and I; X with W; P, N,
   M and Q; F and D.

## 7. Decisions for the owner

1. **The definition:** contextual canonicity (§1.2), each place's
   equivalence generated by laws with a normalizer deciding it.
2. **The places and their requirements** (§3).
3. **The enforcement** (§5): proved, encapsulated, checked at the boundary,
   audited, tested; with the field gates and their probes.
4. **The order:** the heap-knowledge design; then the others.
