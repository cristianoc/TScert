The problem it solves

code adapted from test cases method-effect-map.ts and invalid-map-method-call-effect.ts

If map’s callback calls a method known only by its type, the result may have holes

// Log: a class with a method
// note(n: number): number
function notes(log: Log,
    xs: number[]): number[] {
  const r: number[] =
    xs.map((x) => log.note(x));
  return r;
}

Holes. TScert reads number[] as: every index below the array’s length reads a number. A missing index, a hole, reads undefined, so an array with holes is no number[] to TScert (TypeScript’s own number[] admits one). xs is a number[], so it starts with no holes.

map and its callback. map reads the array’s length once, then visits each index, skipping one that is missing and leaving a hole there in its result. A callback that removes elements of xs during the walk (pop, shift, setting length smaller) makes later indices missing; log.note could, if log holds a reference to xs.

What TScert cannot see. For a call of a non-generic function declaration of the same module that no code reassigns, TScert finds the effect from that function’s code. log.note(x) is a method call, and its code depends on the value: log may be any value of type Log, an instance of a subclass that overrides note or another object of the same shape. So TScert assumes the worst: map’s result may have holes, and the function is refused at the assignment to r.

The answer. The effect is written once, on the method’s declaration, and checked there; every value the program introduces at the type is checked against it, an overriding method where its subclass is declared and any other object where it is passed as a Log; a value from outside code, such as an input of a checked function, is assumed to meet it.
